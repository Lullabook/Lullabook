## Headline

The commit's deterministic suite is genuinely green (`npm run verify` PASS,
139 files / 817 tests — reproduced independently). **But the tests do not prove
the production behavior the tickets require.** Several acceptance criteria are
met only by dead code, unwired services, in-memory fakes, or test seams that
assert report shape rather than real provider/DB behavior. **Tickets 176–185
should NOT be considered release-done.** Five tickets have BLOCKER-severity
gaps between the tested artifact and the production path.

## Confirmed defects, by ticket

Severity: BLOCKER = production path broken / acceptance not actually delivered;
MAJOR = real invariant violated; P1/MINOR = smaller gap.

### Ticket 176 — provider bake-off harness (FINDINGS)
- **MAJOR — "live" canary cannot run real providers.** `tools/provider-bakeoff.ts:9-34`
  wires every adapter op to `unavailable()`; `src/services/provider-bakeoff.ts:397-400`
  states live adapters are not wired. With creds + `$10` it exits 2 with 15 failed
  ops, `$0` cost. The budget/credential gate exists but the research run can't
  execute. (This is the designed gate-hold; the run is a separately authorized
  step. Recorded as MAJOR not BLOCKER because blocking-by-default is intended.)
- **MAJOR — provider/model/endpoint not validated.** `provider-bakeoff.ts:267-279`
  validates only op ID/cost/latency. A broken adapter reporting the wrong FLUX.2
  endpoint or Sonnet model still passes; the test helper copies op metadata into
  the fake result (`tests/176:56-62`), so routing mismatches aren't detected.
- **MAJOR — no real fixture/golden-set/semantic coverage.** Fixture policy is
  declarative metadata (`:10-21`); rubric is an empty template (`:135-153`); tests
  check report shape, not same-input Sonnet scoring or 12-page semantic validity.

### Ticket 177 — R1 plan/entitlement (FINDINGS)
- **BLOCKER — non-Guardian Member can create an Adult Persona.** `persona.ts:79-86`
  checks only the slot before `createAdult` (never `requireCanCreate`);
  `createAtomic` (`:112-131`) checks Guardian role only for Baby, only `selfConsent`
  for Adult. Grader repro: `{"created":true,"role":"member","status":"ready"}` —
  an invited `member` created a Persona despite the R1 Guardian-only rule.
- **MAJOR — entitlement API returns inconsistent legacy caps.** `route.ts:39-44`
  top-level `memberCap`/`capabilities` come from the legacy row (memberCap 4,
  canNarrate true) while nested `plan.limits` is canonical (memberCap 3/1,
  canNarrate false). Probe: `{legacy:{storyCap:8,memberCap:4,canNarrate:true},
  plan:{storyCap:4,memberCap:3,canNarrate:false}}`.
- **MAJOR — concurrent Persona creation exceeds the 3-cap.** `persona.ts:79-86`
  read-only slot check, then async persist at `:280-304`; no reservation/atomic
  DB op. Grader repro with 2 existing: `{"results":["fulfilled","fulfilled"],
  "personaCount":4,"trainCalls":4}`.
- **MAJOR — watchdog failure leaks the allowance reservation.** Normal failures
  call `release` (`storybook.ts:369-376`), but `reapStrandedGenerations`
  (`:385-399`) marks a generating book failed WITHOUT releasing the reservation;
  the ledger stays `"reserved"` not `"released"`.

### Ticket 178 — atomic consent-safe creation (BLOCKER)
- **BLOCKER — `createAtomic` is dead code; production flow moderates AFTER
  persistence.** Independently confirmed: `createAtomic` appears only in
  `persona.ts:112` and its test. The production path —
  `src/lib/actions.ts:130-148` (writes source photos to durable `staging/...`
  blobs BEFORE moderation) → `persona-create` workflow →
  `src/workflows/persona-create-body.ts:35,42` (calls `createAdult`/`createBaby`,
  never `createAtomic`). The tested atomic/consent-safe/moderation-first path is
  not what the native app runs. Violates the core "moderation before durable
  source-photo persistence" criterion.
- **MAJOR — production persistence is not transactional.** `createAtomic`
  compensates in-memory maps, but `SupabaseDataStore.sync()` upserts each table
  independently (`supabase-store.ts:578-716`); a later `babies`/bonds upsert
  failing after the Persona upsert leaves committed rows. In-memory compensation
  can't undo Supabase writes.
- **MAJOR — no real RLS coverage.** `tests/rls-isolation.test.ts` exercises only
  in-memory `DataStore` guards; the 178 Supabase test uses a hand stub whose
  `upsert` only records rows — no PostgreSQL policy is executed. Criterion 7 has
  no real DB coverage.
- **MAJOR — consent/schema "round-trip" isn't a round trip.** `tests/178:199-222`
  hydrates static fixtures and checks the recorded upsert payload; the stub never
  applies it back, so it can't detect column/enum/readback bugs.
- **MINOR — adult self-consent is an unpersisted caller boolean.** `persona.ts:41-46,128-130`;
  no durable consent receipt/association (contrast Baby's Consent-receipt path).

### Ticket 179 — real FLUX LoRA + signed webhook (FINDINGS)
- **P0/BLOCKER — production webhook bypasses the signed/idempotent lifecycle.**
  Independently confirmed: `src/app/api/webhooks/fal/route.ts:19-41` parses JSON
  and `inngest.send(...)` with NO signature/timestamp/body-hash check, and
  forwards the provider URL as `loraWeightKey` (`:30-38`). The verified
  `FalTrainingWebhookService` is NOT wired to this route; `PersonaService` still
  uses the old `startTraining()` path (`persona.ts:251-346`). Signed callbacks,
  owned artifacts, and the real ZIP lifecycle are not active in production.
- **P1 — verification order not exact.** `fal-webhook.ts:44-57` length-checks the
  signature before JSON parseability; required order is timestamp → body hash →
  parseability → signature → business data.
- **P1 — callback idempotency not atomic.** `fal-training-webhook.ts:49-65` checks
  receipts before copying but records after; two simultaneous identical callbacks
  both copy (grader repro: 4 downloads for 2 callbacks). Same check-then-submit
  race at `fal-lora-training.ts:164-196`.
- **P1 — artifact validation is URL/name-only.** `fal-lora-training.ts:215-227`
  doesn't validate content type, non-empty download, JSON config, or LoRA validity.
- **P1 — selected model persisted but not sent to fal.** `adapters/fal.ts:62-78`
  omits `input.model`; model is metadata-only at the provider boundary.

- Clean sub-area: authorization + basic idempotent acceptance (`persona.ts:400-431`)

### Ticket 183 — COGS metering + kill switches (BLOCKER)

- **HIGH — ledger/kill-switch/allowance state not persisted by Supabase store.**
  Migration creates the tables but `hydrateFamily()` doesn't query them and sync
  omits them (`supabase-store.ts:126-165,601-905`). The shared 4-Story allowance
  and cost audit are non-authoritative across requests/processes.
- **MEDIUM — 70% margin floor bypassable when omitted.** `p95FullCapMarginPercent`
  is optional; `evaluateThreshold()`/`authorizeSpend()` enforce the floor only when
  supplied (`provider-cost-metering.ts:85-90,288-307,347-363`).
- Passed: sanitized ledger allow-list, aggregate cost queries, isolated threshold
  classification, isolated kill-switch behavior (isolation only — not wired).

### Ticket 184 — RLS + Hard-delete across artifacts (BLOCKER)
- **BLOCKER — production Hard-delete can't inventory provider artifacts.**
  Independently confirmed: grep for `falTrainingRequests`/`providerCostLedger`/
  `storyAllowanceReservations` in `supabase-store.ts` = ZERO matches. The store
  never hydrates/syncs provider-training/webhook, cost, allowance, or provenance
  records, so in production Hard-delete's maps are empty — remote provider
  deletion is never attempted and limitations can't be reported
  (`hard-delete.ts:68-113`; migration `013_....sql:14-36`).
- **HIGH — Hard-delete idempotency is process-local, not durable.** Independently
  confirmed: `completedGuardianDeletes` is an in-memory `Set` (`hard-delete.ts:41`);
  a new service instance rejects the repeat authenticated delete with an
  authorization error instead of a safe empty report.
- **HIGH — moderation audit rows survive deletion.** Generated-image audits use
  IDs like `${storybookId}/page-${index}` (`storybook.ts:790-794`);
  `hardDeleteFamily()` only matches exact book/member/persona IDs or member-ID
  substrings (`store.ts:633-641`), so those rows aren't removed.
- **HIGH — SQL cost-ledger retention contradicts in-memory policy.** Migration
  declares `provider_cost_ledger.family_id ... ON DELETE CASCADE` (deletes
  financial evidence with the Family) while the in-memory impl retains sanitized
  ledger rows post-delete (`013_....sql:38-55` vs `store.ts:702-724`).
- Passed: in-memory cross-Family denial, local blob inventory, provider-degraded
  limitation reporting, consent-triggered purge, same-process repeat.

### Ticket 185 — R1 provider e2e gate (BLOCKER)
- **BLOCKER — not actually an end-to-end gate.** `runR1ProviderE2E()` runs only 3
  abstract ops (training, Story text, Page fan-out; `r1-provider-e2e.ts:182-210,
  317-354`); it does NOT exercise the native flow, Supabase, consent, roster/Babies,
  Persona review, 12 real Page jobs, recovery, RLS, or Hard-delete. The report
  returns a 16-step plan with every step permanently `pending` (`:383-385`), and
  the shipped tool hardcodes `liveAdaptersWired:false`.
- **HIGH — fake/missing evidence can become release-eligible.** A non-dev adapter
  returning success with no request IDs gets synthetic IDs
  (`r1-page-fanout:missing-request-id`); eligibility checks only adapter flags +
  nonempty evidence + success status, not real request IDs or
  provider/endpoint/model validation (`:325-339,361-368`). Grader probe produced
  `releaseEvidenceEligible:true` with all-synthetic IDs.
- **HIGH — redaction leaks JSON secrets.** `redactLog()` matches only unquoted
  `key=value`/`key:value`; JSON like `{"apiKey":"TOPSECRET","photo":"PRIVATE"}`
  passes through into the report (`:288-293,387-388`). Grader probe confirmed both
  secrets retained. (PII/credential hygiene gap.)
- Passed: credential/budget config checks, blocked-by-default, fixture-policy
  declaration, isolated economic gate checks, dev-adapter exclusion.
